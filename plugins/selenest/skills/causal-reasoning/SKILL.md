# 因果の法則

結果を望むだけでなく、その結果を生む原因と条件を確かめ、働きかけを選ぶ。
仏教の縁起に着想を得て、因となる原因だけでなく、縁となる成立条件も見る。因と縁の分類を固定せず、何がどう結果に関わるかを具体化する。
これは実務への応用であり、仏教の教説を技術的効果の証明に使うものではない。個別の因果関係は、資料・コード・観測・実験で検証する。
トークン数の節約や回答を短くする都合で、原因・条件・対策・結果の検証を省かない。
一部の症状や指標だけの改善で終えず、問題全体の解消、再発防止、ほかの箇所への影響まで確かめる。

## 適用条件

設計や技術の採用理由を示す時、改善策の効果を見積もる時、レビューで原因から対策・結果への説明に飛躍がある時に使う。
根本原因の究明や再発防止を扱う場合は、まず[nazenaze](../nazenaze/SKILL.md)で枝ごとに原因を掘り下げ、その後に本スキルで対策の効き方を検証する。
根本原因、そこに至る連鎖、根拠、未確定の原因候補を引き継ぐ。既に探索済みなら繰り返さず、検証で不足が見つかった枝に戻る。

用語や仕様の説明、好みだけで決める選択、因果関係と効果が確認済みの定型作業には、分析を追加しない。
緊急時は復旧や被害抑制を優先し、検証の完了を待たせない。

## 進め方

### 1. 結果と現在の差を定める

何がどうなれば成功か、現在は何が起きているかを、対象・条件・観測できる振る舞いや指標で示す。必要なら達成時期も定める。
「DIがない」のような手段の不在を問題にせず、何ができず困っているのかを押さえる。設計段階の懸念は、発生済みの事実と区別する。
会話・資料・コード・ログ・テスト結果を先に確認し、質問は判断を左右する不足に絞る。

### 2. 原因と成立条件を捉える

何が、どの条件で、どのように現在の結果を生むのかを説明する。各つながりについて、次を区別する。

- 事実：確認した内容と、その根拠の所在・観測条件。
- 仮説：何が何を引き起こすと考えるか、その仕組みと未確認の箇所。
- 成立条件：仕組みが働くために必要な条件と、各条件が確認済みかどうか。

同時に起きたことや時間的な前後関係だけで、因果関係を断定しない。
複数の原因や条件が組み合わさる場合は分岐や合流を残し、単一の根本原因に押し込めない。失敗という結果だけから個人の行いや責任を決めつけない。
なぜなぜから引き継いだ原因候補は、根拠を確認するまで仮説のまま扱う。根本原因という呼び名だけで確定済みとみなさない。

### 3. 対策から結果までをつなぐ

「対策 → 原因や条件の変化 → 中間の変化 → 望む結果」を具体的な動作で説明し、各つながりの根拠と成立条件を添える。
根本原因の分析を経た場合は、原因ごとに対策を対応させ、途中の症状への処置と、根本原因への働きかけを区別する。
複数の対策を組み合わせる時は、対処されない原因が残らないか、対策同士が効果を妨げないかを確認する。
仕組みの名前を採用理由にせず、どこへの働きかけが結果を変えるのかを示す。矢印を描けたことを証明とは扱わない。

問題を生む条件を取り除く方法と、望む結果に必要な条件を整える方法を検討する。
ある原因を取り除いても、別の原因が残る場合や、既に生じた損害が戻らない場合がある。原因の除去だけで回復や目標達成に十分だと決めない。
その対策が不可欠か、ほかの方法でも達成できるか、追加の条件や対策が必要かを確認する。
副作用や負担が別の経路で目標を損なわないか、指標だけが変わって問題が残る可能性も調べる。

### 4. 代替説明と照合して確かめる

判断を左右するつながりについて、同じ観測を説明できる別の原因、反例、条件が変わると成立しない場合を検討する。
例えば、共通の原因が両方を変えた可能性、因果の向きの逆転、同時に行われた別の変更を疑う。対策をしなくても結果が変わった可能性も考える。

仮説が正しい場合と別の説明が正しい場合で、何の観測が変わるかを示す。
結果を見る前に、比較する状態、途中と最終結果で観測する項目、成功条件、仮説を見直す条件を定める。
どの仮説でも起きる観測だけなら、それでは見分けられないと明記する。

検証方法の厳密さは、誤判断の影響、やり直しやすさ、不確実性に合わせる。これは分析を短く打ち切る基準ではなく、必要な根拠を得る方法を選ぶ基準である。
小さな判断はコード・仕様の確認や条件を絞った再現テストから始める。効果量やばらつきが選択を左右する場合は、比較実験や適切な因果推論を検討する。
実施前後の比較では、負荷・対象・同時変更などの違いを確認する。比較条件をそろえられなければ、その限界を残す。

実施できる確認を行い、観測を予測と照合する。想定と異なれば、原因・仕組み・成立条件を見直す。
新しい説明は新しい仮説として扱い、都合のよい観測だけを残したり、事後に成功条件を変えて正当化したりしない。

### 5. 根拠に応じて選ぶ

候補を、原因への作用、期待する結果、成立条件、副作用、負担で比較し、採用・条件付きの試行・不採用・保留を選ぶ。
重要な仮説を見分ける根拠が得られない場合は、判断を保留し、次に何を観測すれば判断が変わるかを示す。
検証計画と実施結果を区別し、未検証の効果や、確認した条件を超えた一般化を断定しない。

## 終了基準

- 現在と目標の差、原因への作用、結果に至る仕組みと成立条件を、根拠の状態とともに追える。
- 重要な代替説明・反例・追加条件・副作用を検討し、選択理由と効果の確認方法が具体的になっている。
- 根本原因の分析を経た場合は、各原因への対処と、問題全体の解消・再発防止までのつながりを確認し、未対処の原因や影響を明示している。
- 判断を左右する不明点が残らないか、条件付きの試行や保留として扱い、次の確認を定めている。

この条件がそろえば検討を区切る。検討の終了を、効果の実証や問題の解決と同一視しない。
出力は、結論、因果のつながりと根拠、残る条件、確認結果または次の確認が追える長さにする。小さな判断で全項目を独立した節にする必要はない。

## 使用例

相談：「DIを導入すればテストしやすくなるので採用したい」

コードの確認で、判断処理が内部で実APIを呼ぶと分かった場合を考える。目標を「実APIなしで判断処理の分岐を検証できる」とする。
対策案は「通信を差し替えられる境界を設ける → テスト用の回答を渡せる → 実APIなしで判断処理を検証できる」である。
ただし、判断処理に実通信への別経路がなく、必要な回答や失敗をテスト側から与えられることが成立条件になる。

通信を禁止した状態で固定回答と失敗を渡し、外向き通信がなく、期待する分岐を検証できるか確かめる。
共有データや現在時刻も結果を左右するなら、通信の差し替えだけでは再現性は得られない。テスト用の回答と実APIの不一致もあり得るため、境界の契約は別途確認する。
手動で依存先を渡す案や、取得済みの値を判断処理に渡す案も比べる。DIコンテナーの必要性は別に判断し、未実施なら効果は仮説として残す。
