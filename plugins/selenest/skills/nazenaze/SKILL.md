# なぜなぜ

原因の連鎖を遡り、問題を生む上流の条件や仕組みである根本原因を探す。
「なぜ」の回数を固定せず、直前に得た原因がなぜ生じたかを繰り返し問う。根本原因は複数あり得る。
トークン数の節約や回答を短くする都合で、原因の枝や根拠の確認を省かない。
目先の症状を直せる対策が見つかっても、根本原因の探索を打ち切らない。問題全体の解消と再発防止まで考える。

## 適用条件

不具合や作業上の問題の原因を調べる時、再発防止策を考える時、設計や改善案が何を解決するのかを確かめる時に使う。
レビューや会話で「なぜ？」と問われた時は、直前の主張の根拠と、その背後にある原因を確認する。

用語や仕様の説明だけで答えられる質問、原因と対策が確認済みの定型作業には、分析を追加しない。
緊急時は復旧や被害の抑制を優先し、原因分析の完了を待たせない。応急処置と再発防止策は区別する。

## 進め方

### 1. 問題を具体化する

観測した事実、望ましい状態、その差を明確にする。発生する条件や範囲も押さえる。
設計段階でまだ発生していない問題は、想定するリスクとして区別する。
「DIがない」のような手段の不在を、そのまま問題にしない。何ができず、どんな支障があるのかを示す。

会話、既存資料、コード、ログ、テスト結果から分かることを先に確認する。
ユーザーへの質問は、資料では分からず判断を左右する点に絞り、関連する質問をまとめる。

### 2. 原因を掘り下げる

問題に対して「なぜ起きたのか」を問い、得た回答から原因となる事柄を取り出す。
その事柄を次の問いの対象にして、「なぜその原因が生じたのか」を問う。この操作を枝ごとに繰り返す。

- 回答に複数の原因が含まれる場合は分岐し、それぞれを次の問いの対象にする。元の問題に対する説明を横に並べるだけで終えない。
- 各段階で「問いの対象 → 原因としての回答 → その回答を対象にした次の問い」を追えるようにする。原因と、その原因が生む結果とのつながりに根拠を添える。
- 直前の回答の言い換えや「仕組みがなかった」で止めず、なぜその状態が生まれ、維持されたかを調べる。
- 対策を思い付いたことを終了理由にしない。途中の原因を取り除いても、上流の条件によって同じ問題が再び生じないかを確かめる。
- 確認済みの原因、原因の仮説、未確認事項を区別し、根拠の所在や確認結果を添える。
- 同時に起きたことや、もっともらしい説明だけで因果関係を確定しない。発生しない条件や反証も調べる。
- 複数条件が組み合わさって起こる可能性や、別の枝が同じ原因に合流する可能性も残す。
- 「注意不足」「理解不足」で止めず、必要な情報、手順、作業環境、検知や防止の仕組みのどこに不足があるかを調べる。個人への責任追及に置き換えない。

### 3. 根拠の不足を調べる

根拠が不足したら、推測をつないで掘り下げず、次に確かめる問いを定める。
「何を確認すれば、どの仮説を支持または棄却でき、対策の選択がどう変わるか」を示し、資料の確認、再現、条件の比較、小さな実験から適切な方法を選ぶ。
技術や実現方式を比較する調査が必要なら、[technical-discoveryスキル](../technical-discovery/SKILL.md)を使用する。

確認できる資料や実験があれば調べ、結果を踏まえて該当する枝の掘り下げを続ける。
確認できない場合は、未確定の原因候補と、そこで調査を止める理由、判断への影響、次の確認方法を示す。最後に得た回答を自動的に根本原因と呼ばない。

### 4. 根本原因に対する対策の因果関係を検証する

各枝で得た根本原因、そこに至る連鎖、根拠、未確定の原因候補を整理してから、[因果の法則](../causal-reasoning/SKILL.md)を適用する。
各対策について、どの根本原因に作用するか、何が変わり、なぜ問題の解消や再発防止につながるかを検証する。
原因候補が未確定なら、その仮説が正しい場合の対策として扱う。対策の検証で原因の不足が分かった場合は、該当する枝に戻る。
確認方法には、比較する実施前の状態、観測する指標やテスト、成功と判断する条件を含める。
導入したい技術から逆算せず、原因に作用する必要十分な変更を選ぶ。対策が複数ある場合は、効果と負担を比べる。
効果を確認していない段階では解決済みにせず、期待した効果が出なければ原因の仮説を見直す。

## 終了基準

次の条件がそろえば、根本原因の探索を区切り、対策の検証へ進む。

- 主要な枝について、直前の回答を対象にした掘り下げが行われ、問題から根本原因までの連鎖を根拠とともに説明できる。
- 根本原因と判断した各原因について、それを生む上流の条件も検討し、そこで探索を区切れる理由が説明できる。
- 未確認の枝や仮説が隠されておらず、根本原因の判断や再発防止策を左右する場合は、必要な確認が行われている。

判断を左右する根拠が得られない場合は、解明したと扱わず分析をいったん区切る。確認方法が決まっただけでは、その枝の根本原因が判明したことにはならない。
未確認事項と次の調査・実験、または判断を保留する理由を示す。
結果は、問題、原因と根拠、未確認事項、対策と効果の確認方法が追える長さにまとめる。

## 使用例

相談：「テストしやすくするためにDIコンテナーを導入したい」

まず何の検証に支障があるかを確認する。次は、コードと設計記録で回答を確認できたと仮定した例である。

1. なぜ判断ルールのテストに実APIが必要なのか？ → 判断処理の内部で実通信のクライアントを生成しているため。
2. なぜ内部で実通信のクライアントを生成する設計になったのか？ → 設計時に実APIへ接続する使い方だけを想定し、依存先を外から渡す経路を設けなかったため。
3. なぜ実APIへ接続する使い方だけを想定したのか？ → テスト方針が結合テストだけを対象とし、判断ルールを単独で検証する要件を扱っていなかったため。

次は「なぜそのテスト方針になったのか」を調べる。記録がなければ原因候補と確認先を残し、方針の不備を根本原因と断定しない。
共有データも不安定さの原因なら、共有が生じた理由を別の枝として掘り下げる。
各枝の根本原因を整理してから、通信の分離やテスト方針の見直しが各原因にどう作用するかを因果の法則で検証する。通信を分離する案が浮かんだ段階で、探索を終えない。
